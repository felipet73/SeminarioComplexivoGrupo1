# ADR-0004 — Preparar PostgreSQL para estado administrativo duradero

Estado: **preparado y probado localmente; activación diferida por decisión de costos del equipo, 8 de noviembre de 2026 (Ecuador)**. Se conservará SQLite en producción y se activará PostgreSQL/Cloud SQL oportunamente, con presupuesto aprobado, migración y validación remota. No hay fecha comprometida ni autorización actual para aprovisionar. La persistencia administrativa remota permanece parcial.

## Problema

La semilla SQLite de la imagen recupera el corpus base, pero Cloud Run descarta el disco de instancia. Cargas, archivos originales, índices, prompts y decisiones posteriores no sobreviven de forma compartida. `RAG_DATA_DIR` no crea un volumen y Cloud Storage FUSE no es una solución de bloqueo para SQLite.

## Decisión propuesta

Añadir un backend PostgreSQL optativo mediante `RAG_DATABASE_URL`, manteniendo SQLite como default. Conservar contratos JSON y SQL parametrizado; registros, auditoría, fragmentos, vectores/caché y archivos originales se guardan transaccionalmente en la misma base. No incorporar GCS/pgvector para el volumen pequeño actual: los originales van en BYTEA y el coseno sigue en Python. La búsqueda léxica usa FTS español/ts_rank_cd en PostgreSQL y FTS5/BM25 en SQLite; no son algoritmos idénticos.

Usar Cloud SQL Client con la cuenta de ejecución, socket nativo y credencial SQL exclusiva en Secret Manager; no DSN en Git, frontend, Terraform o argumentos. Para otro PostgreSQL remoto se exige TLS verify-full. Las operaciones de estado se serializan con advisory lock transaccional entre procesos. Mantener máximo una instancia durante esta etapa; no se implementa un ejecutor distribuido de experimentos.

## Migración, comprobación y recuperación

Exportación administrativa protegida de una copia SQLite y archivos; importación explícita a destino vacío, verificación de hashes, rechazo de sobreescritura y transacción completa. Acordar ventana sin escrituras; no se promete migración en vivo. Las sesiones en memoria se invalidan con el proceso y requieren nuevo login. Los trabajos en curso pueden quedar interrumpidos; sus resultados parciales se conservan, no su ejecución.

Ensayo local: dos procesos nuevos, archivos/índice/configuración/prompts/auditoría/vectores preservados, rollback y reautenticación; golden set léxico PostgreSQL 14/16 + 4/4. La semilla SQLite también se verifica en dos contenedores nuevos. Falta activar Cloud SQL y repetir prueba remota antes de cerrar s4c.

## Costos y alternativas

La propuesta Terraform es PostgreSQL 17, Enterprise zonal, db-f1-micro y SSD 10 GB, backups diarios retenidos siete y sin PITR. Es una base de demostración económica a cotizar, no una promesa de SLA/capacidad productiva. No se aprovisionó: el equipo decidió posponer su activación por costos y conservar la opción lista para retomarla oportunamente. Confirmar cálculo mensual, presupuesto y respaldo antes de apply.

Migrar a servicio durable evita depender de una única instancia Cloud Run; no elimina la necesidad de backups, alertas, migraciones ni pruebas. Quitar la variable para volver a SQLite perdería de vista los cambios escritos en PostgreSQL: no es rollback sin pérdida. Ver [procedimiento completo](22-postgresql-cloudsql.md).
